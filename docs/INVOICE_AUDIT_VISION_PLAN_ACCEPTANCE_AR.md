# وثيقة الرؤية والمتطلبات وخطة التنفيذ والقبول — محرك تدقيق فواتير الموردين المبني على MDIA

**الإصدار:** 1.0 — 2026-11-19  
**الحالة:** مرجع تأسيسي معتمد للنقاش والتنفيذ المرحلي؛ ليس تصريحاً بأن المنتج جاهز للإنتاج  
**المستودع الأساسي:** [overurdream-collab/OCR_deepseak](https://github.com/overurdream-collab/OCR_deepseak)  
**الفرع المرجعي عند إعداد الوثيقة:** `main`؛ تُضاف هذه الوثيقة أولاً في فرع توثيق مستقل  
**اسم العمل المقترح:** Invoice Audit Engine / محرك تدقيق الفواتير  
**الأولوية:** الموثوقية والأدلة والتدقيق قبل التلقائية وسرعة القراءة  
**قاعدة السلامة:** لا تُستنتج ولا تُخمن أي قيمة مالية؛ غير المثبت لا يُعتمد.

> **الرؤية الأساسية:** نريد أن يعمل النظام **مثل مدقق مالي، لا مثل آلة OCR تقرأ الأرقام وتتوقع أنها صحيحة**. دور OCR هو اقتراح قراءة للنص؛ دور النظام المالي هو تقييم الأدلة، ومطابقة المستندات، وإظهار الاستثناءات، ومنع أي اعتماد غير مؤسس. اتفاق محركي OCR ليس دليلاً مستقلاً على صحة القراءة، وصحة الحساب لا تثبت صحة الحدث التجاري.

## 1. الغرض والمشكلة التجارية

شركات المشتريات والتوزيع والمستودعات والمحاسبة تقارن أوامر الشراء (PO)، وإشعارات استلام البضاعة (GRN)، وفواتير الموردين (Invoice)، وربما العقود والمرتجعات والإشعارات الدائنة وأذونات الدفع. قد تختلف الكميات أو الأسعار أو الوحدات أو الأصناف أو المورد أو العملة. المراجعة اليدوية مرهقة، لكن الاعتماد الآلي بناء على OCR غير موثوق أخطر من العمل اليدوي.

لا نبيع وعد «OCR بدقة 100% لأي مستند»؛ نبيع مسار تدقيق يستطيع **شرح سبب كل نتيجة** وإرجاعها إلى بيانات المصدر وقواعد معروفة وسجل قرار قابل للمراجعة. لا توجد ضمانة مطلقة أن OCR أو بيانات المورد أو إشعار الاستلام صحيح 100%. نهدف إلى **صفر أخطاء مالية صامتة مرصودة في كل مجموعة اختبار معروفة**، وإلى نظام يغلق المسار عند عدم كفاية الدليل؛ لا نعلن ضمان عدم حدوث خطأ مستقبلاً.

### 1.1 النتائج التي نريدها
1. تقليل زمن مطابقة الفواتير دون نقل عبء الأخطاء إلى العميل.
2. اكتشاف الفواتير المكررة، فرق الكمية والسعر والعملة والضريبة والخصومات وعدم تطابق المورد/الطلب.
3. تمييز صريح بين «مطابق ضمن نطاق الإثبات»، و«اختلاف مثبت»، و«تعذر التحقق/ينتظر المراجعة».
4. تمكين الموظف من فتح مصدر كل مبلغ ومقارنته بصفحة/خلية/حقل مرجعي وحفظ قرار التصحيح والتوقيع.
5. تشغيل محلي أولاً وبتكلفة برمجيات منخفضة، مع إمكان التوسع لاحقاً إلى خدمة للشركات، دون تعريض المستندات الحساسة للخدمات العامة افتراضياً.

### 1.2 ما ليس هدفاً
- لا نقبل الفواتير تلقائياً اعتماداً على درجة ثقة OCR.
- لا نستنتج قيمة مطبوعة ناقصة من `quantity × price` ثم نقدمها كأنها موجودة في الفاتورة؛ الحساب مسموح **للكشف عن الاختلاف** فقط.
- لا نستنتج واقعة الاستلام الفعلي من ملف فقط.
- لا نغيّر المستند الأصلي بعد استلامه ولا نطمس القراءة الأصلية عند التصحيح.
- لا نبني ERP كاملاً أو بوابة دفع أو خدمة سحابية من المرحلة الأولى.
- لا ندّعي تحقيق 100% معالجة تلقائية لجميع الصور والكتابات اليدوية.

## 2. الوضع الحالي الفعلي في المستودع

### 2.1 ما تحقق في الملفات المقروءة

المستودع الحالي هو **MDIA — Medical Document Intelligence Agent**، محرك محلي لقراءة ملفات PDF طبية وعربية/إنجليزية واستخراج بيانات منظمة مع أدلة مصدرية. وهو أصل هندسي يمكن إعادة استخدام **مكوناته العامة** دون تحويل أو إفساد اختصاصه الطبي.

من `README.md` و`mdia/server.py` يتوفر حالياً:
- واجهة HTTP محلية، رفع PDF، إدارة jobs، إعادة المعالجة والتصحيح، عرض صور الصفحات والأصل.
- تصدير JSON/CSV/XLSX/PDF وفق الوظائف الموثقة.
- دعم النص العربي والاتجاه RTL والأرقام الهندية والفواصل؛ قراءة نص PDF وOCR للصور.
- احتفاظ بالقيمة والنص الخام، وصفحة المصدر والموضع وطريقة الاستخراج والثقة، وسياسة إحالة القيم الغامضة للمراجعة.
- تشغيل Windows وDocker وتعليمات تشخيص محلية.
- مكونات Python مثل `pdfplumber` و`pypdfium2` و`pytesseract` و`openpyxl` وفق `requirements.txt`. يصف README مسار PaddleOCR CPU، لكن يجب التحقق منه في التشغيل الفعلي لكل نسخة.

**تحذير مهم:** على الرغم من اسم المستودع، **DeepSeek-OCR ليس مثبتاً أنه مدمج أو مستخدم في المسار الحالي**؛ يؤكد README أن DeepSeek-OCR 2 غير داخل البرنامج الأساسي. لا تُنسب أرقام نجاح MDIA إلى DeepSeek. أي إضافة DeepSeek تكون تجربة مقارنة منفصلة تراجع تراخيصها ومتطلبات GPU ونتائجها.

### 2.2 الوضع المثبت للاختبارات

تقرير القبول القديم بتاريخ 2026-10-25: معالجة 300 فاتورة طبية اصطناعية عبر PaddleOCR CPU بدون أعطال تشغيل، بدقة حقول `4,895 / 5,776 = 84.75%` و99 صفاً إضافياً و300/300 بحاجة إلى مراجعة بشرية. هذا **ليس تصريحاً بالدقة المالية أو نجاح المطابقة**.

وثيقة التسليم `docs/AGENT_HANDOFF_AR.md` بتاريخ 2026-11-02 تسجل رأس PR #32 التجريبي ونتيجة اختبار فاشلة: `5,573 / 5,776 = 96.48%`، أي 203 حقول مفقودة/خاطئة و11 صفاً إضافياً و300/300 مستند في المراجعة؛ لا تمر بوابة القبول المطلوبة. هذه **نتيجة موثقة تاريخياً للفرع التجريبي لا دليلٌ على الحالة الحية عند كتابة هذه الوثيقة**. يلزم التحقق مجدداً من حالة PR وActions وSHA قبل أي دمج.

تكشف `docs/MDIA_300_FIELD_FAILURE_ANALYSIS_AR.md` أن عيب ربط **صفوف الجداول العربية بأعمدتها** مهم، خصوصاً في المخططات العربية المختلطة. وتشرح `docs/PADDLE_ARABIC_GEOMETRY_AUDIT_AR.md` أن مواضع الكلمات المستنتجة من صناديق السطور لا تعد إثباتاً هندسياً مستقلاً.

## 3. القرار المعماري

نفصل **محرك القراءة العام** عن **محرك التدقيق المالي**:

```text
[PO] [GRN] [Invoice] [Credit Note / Contract / Supplier Master]
                  |
       Intake + Immutable Originals
       SHA-256 + source metadata + access control
                  |
     File classifier + safety/quarantine
          /                 \
 Structured/XML/Excel   PDF text / scanned image
   native parsing         OCR candidate extraction
          \                 /
          Provenance-aware field extraction
          Raw text + page/coordinates/cell/path + parser/model version
                  |
    Schema validation + field evidence verification
                  |
        Document & item identity resolution
                  |
  Deterministic 2-way / 3-way matching engine
     Decimal, units, currency, dates, tolerances
                  |
   VERIFIED_MATCH / VERIFIED_EXCEPTION / UNVERIFIABLE
                  |
    Human review + signed decision + immutable audit log
                  |
   Evidence-backed report / export / ERP integration later
```

- **MDIA** يبقى نواة قابلة لإعادة الاستخدام في القراءة والتتبع/التصحيح دون إدخال قواعد تدقيق الموردين في `mdia` الطبي مباشرة.
- **Invoice Audit Engine** منتج أو حزمة مستقلة تعتمد واجهة واضحة لمدخلات القراءة ونتائجها. يتم تقرير موضعه (مستودع مستقل أو حزمة ضمن mono-repo) بعد فحص اعتمادات الشفرة الفعلية؛ لا يُفرض إعادة كتابة MDIA.
- **الذكاء الاصطناعي لا يصدر اعتماداً مالياً**؛ يلخص أو يقترح استخراجاً أو تشابه صنف/وصف، بينما المطابقة والاستثناءات تطبق قواعد مُعرّفة ومختبرة. مطابقة الهوية الغامضة تتطلب إثباتاً أو موافقة بشرية.

## 4. أصناف المصادر وكيف تُقرأ

### A. الفاتورة الإلكترونية المهيكلة
استقبال XML/JSON وفق مخطط معروف (مثل Peppol BIS Billing 3.0 إن كان متاحاً، أو صيغة ERP محددة). قراءة أصلية غير احتمالية، تحقق مخطط، أنواع الحقول، التواقيع/القناة الموثوقة إن وجدت، ومطابقة معرفات البائع والمستند. **الصحة التركيبية ليست دليلاً أن الكمية أو التوريد حقيقيان**.

### B. ملفات Excel / CSV / ERP
استخراج مباشر للقيم الأصلية دون OCR، حفظ اسم الملف واسم الورقة وعنوان الخلية والمعادلة والقيمة المخزنة إن وُجدت، وملاحظة اختلاف نتائج الصيغ/التنسيقات. منع تنفيذ ماكرو أو معادلات خارجية غير موثوقة؛ لا نفترض أن الخلية الصحيحة المصدر صحيحة المعنى.

### C. PDF نصي
استخراج نصوص ومربعات وجداول عبر قارئ PDF وإعادة بناء التخطيط. لا نثق بترتيب النص وحده في المستندات متعددة الأعمدة أو RTL؛ التباس صف/عمود = إحالة للمراجعة.

### D. PDF مصور وصور الهواتف
تهيئة الصورة (اتجاه، ميل، حدود، جودة) ثم OCR محلي. PaddleOCR هو خيار البداية، وDeepSeek-OCR أو PaddleOCR-VL محركات مقارنة محتملة *بعد اختبار عملي وترخيص*. أي قيمة OCR تحمل `provisional` حتى يكتمل تحقق الأدلة المطلوب؛ يمكن استخدام مراجعة مستقلة أو أصل رقمي معتمد. **اتفاق نموذجين ليس برهاناً قاطعاً**.

### E. غير مقروء/يدوي/ملتبس
لا قيمة مفترضة، لا استكمال بالتخمين، لا تحويل «ريال» إلى YER/SAR دون قرينة معتمدة، ولا تفسير تاريخ مبهم دون قاعدة واضحة. النتيجة: `UNVERIFIABLE`.

**أولوية القراءة:** بيانات أصلية مهيكلة موثوقة → استخراج رقمي مباشر → OCR مساعد → مراجعة بشرية. لا نستخدم OCR إن كانت بيانات أصلية قابلة للتحقق متاحة.

## 5. سلسلة إثبات القيمة Evidence Chain

كل قيمة مالية أو كمية أو هوية تجارية يجب أن تحمل سجلاً مثل:

```json
{
  "document_id": "doc-uuid",
  "document_sha256": "<SHA256 of immutable original>",
  "document_type": "invoice",
  "field": "items[0].unit_price",
  "raw_text": "50.00",
  "normalized_value": "50.00",
  "currency": "USD",
  "source": {
    "kind": "pdf_page_region",
    "page": 1,
    "bbox": [100, 200, 160, 224],
    "text_span": "50.00"
  },
  "extraction": {
    "engine": "native_pdf_or_ocr",
    "version": "pinned-version",
    "model_hash": null,
    "confidence": null
  },
  "verification": {
    "state": "provisional",
    "reason_codes": [],
    "reviewer_id": null,
    "reviewed_at": null
  }
}
```

المثال أعلاه **مخطط مقترح، وليس صيغة موجودة حالياً في الكود**. للـExcel نستخدم `sheet/cell`، ولـXML `xpath/element-id`، ولـAPI المصدر `record-id` ومعلومات القناة. لا نعتمد bbox مشتقاً حسابياً من صندوق السطر بوصفه إثباتاً مستقلاً لموضع الكلمة. نحفظ نسخة الأصل غير قابلة للتعديل وتاريخ وصولها، ونسخة القراءة الخام، وتصحيحاً منفصلاً مع مبرر واسم مراجع وزمن القرار.

**بصمة SHA-256** تكشف تبديل المحتوى بين النسخ؛ لا تثبت وحدها هوية المُصدر أو صحة البيان. يلزم توقيع رقمي معتمد/قناة موثوقة/تأكيد مستقل عندما يكون إثبات المصدر شرطاً للمطابقة.

## 6. العقد الموحد للبيانات Schema

الحد الأدنى المقترح:

- `Document`: id، type (PO/GRN/INVOICE/CREDIT/RETURN/CONTRACT)، source hash، version، owner tenant، المصدر، status.
- `Party`: supplier id، tax id (إن وجد)، الاسم وأسماء بديلة مثبتة، حساب/عنوان حسب الحاجة.
- `Header`: رقم المستند، تاريخ الإصدار، مرجع PO/GRN، العملة وفق ISO 4217، ضرائب/خصومات/نقل، الإجمالي المنشور.
- `Line`: رقم المصدر، SKU/GTIN/part number، وصف خام، وصف منظم، وحدة قياس، كمية Decimal، سعر Decimal، خصم وضريبة Decimal، line total الأصلي.
- `Evidence`: مصدر القيمة الكامل وإصدار القارئ/الموديل ونتيجة التحقق.
- `Link`: علاقة فواتير ↔ أوامر شراء ↔ استلامات، مع احتمال عدة استلامات/عدة فواتير/تسويات جزئية.
- `Finding`: rule_id، شدة، تفاصيل المتوقع والملاحظ ومصدر كل قيمة، affected lines.
- `Decision`: حالة القرار، المستخدم، صلاحياته، السبب، توقيت وتوقيع تدقيقي، الإصدارات.

**الأموال:** Decimal أو أعداد صحيحة في أصغر وحدة بحسب سياق العملة؛ لا float ثنائي في القواعد المالية. نحدد قواعد التقريب الضريبي حسب السوق/العقد؛ لا ندمج عملات مختلفة ولا نحسب فروقات بين العملات دون سعر صرف موثق بتاريخ وسياسة معتمدة. تخزن قيمة الأصل والوحدة كما وردت، وأي تحويل وحدات مستند إلى جدول تحويل مُجاز.

## 7. قواعد المطابقة المالية

### 7.1 التحقق السابق للمطابقة
- سلامة المصدر وسلسلة الأدلة واكتمال المستند.
- منع تكرار المصدر واستلام نسخ متعددة من الفاتورة نفسها دون إصدار/تعديل واضح.
- التحقق من معرف المورد واتساق الفاتورة مع PO، والعلاقة بين PO وGRN وInvoice.
- التحقق من التاريخ/العملة ومجال العقد والعروض والضرائب.
- فحص `sum(lines) + charges + taxes - discounts = stated_total` طبقاً لسياسة التقريب الفعلية؛ **لا تصحيح تلقائي للمبلغ المنشور**.
- الهوية: لا تكفي مشابهة الأسماء؛ SKU أو مرجع موحد أو خريطة مرادفات معتمدة، وإلا `UNVERIFIABLE`.

### 7.2 مطابقة ثنائية/ثلاثية
- **2-way**: مقارنة فاتورة المورد بأمر الشراء في الحالات المعتمدة بسياسة المؤسسة.
- **3-way**: مقارنة PO + GRN + Invoice عند شراء مواد مستلمة. يُراعى الاستلام الجزئي والفواتير المتعاقبة والمرتجعات والإشعارات الدائنة، مع عدم احتساب الكمية المستلمة أو المفوترة مرتين.
- الفروق في الكمية وسعر الوحدة والعملة والضرائب والخصومات ورسوم النقل/الشحن تعاد كاستثناءات منفصلة.
- سياسة التسامح (tolerance) تُحدد صراحةً وتُصادق عليها المؤسسة، ولا تؤدي تلقائياً إلى إخفاء فرق مالي. تُظهر التقارير الفرق الخام حتى عند قبول فرق داخل الحد المسموح.
- لا يتحول مستند «مراجعة مطلوبة» إلى مستند مطابق بسبب مجرد تخفيض threshold.

### 7.3 مثال محاسبي
PO: كابل 100 × 5 USD، وقاطع 50 × 12 USD.  
GRN: كابل 90، قاطع 50.  
فاتورة: كابل 100 × 5، قاطع 50 × 13 = 1,150 USD.  
تظهر ملاحظتان: 10 كابلات مفوترة لم تسجل مستلمة = 50 USD؛ فرق سعر قاطع 1 × 50 = 50 USD.  
الإجمالي المقارن للكمية المستلمة **بأسعار PO** = 1,050 USD، قبل الضرائب/المصاريف/التسويات، ولا يُسمى هذا «مبلغ الدفع المستحق» قبل الرجوع للعقد وسياسة الاستلام. المحرك **لا يعيد كتابة الفاتورة**؛ يربط كل نتيجة بموضع السعر والكمية في مصادرها.

## 8. حالات القرار — لا تساوي القراءة بالمطابقة

1. **VERIFIED_MATCH / مطابق ضمن نطاق القواعد المعتمدة**: جميع الحقول الحرجة المطلوبة موثقة، علاقات الأطراف والمرجع صحيحة، القواعد ذات الصلة ناجحة، ولا اختلاف غير محلول. «مطابق» لا يعني أن المورد صادق خارج حدود الدليل أو أن الاستلام وقع فعلياً.
2. **VERIFIED_EXCEPTION / اختلاف مثبت**: اختلاف موصوف بأرقام من مصادر موثوقة؛ لا يبرر الاعتماد الآلي، وقد يحتاج مراجعة المورد أو المستودع.
3. **UNVERIFIABLE / تعذر التحقق**: قيمة/مستند/هوية/علاقة/دليل غير واضح أو ناقص أو متعارض. **ليس** «مطابقاً» ولا «غير مطابق مؤكد».
4. **REVIEWED_ACCEPTED / اعتماد بشري موثق**: يظل منفصلاً عن قرار محرك القواعد؛ يوضح المراجع استثناءاته وتفويضه ولا يتظاهر أن قراءة OCR كانت صحيحة أصلاً.
5. **REJECTED / مرفوض** و**SUPERSEDED / مستبدل بتصحيح**: وفق مسار مراجعة وحوكمة واضحين.

**Fail-closed:** فشل parser/OCR أو خطأ في جودة المصدر أو عدم مطابقة الأدلة أو مشكلة نظامية يمنع أي `VERIFIED_MATCH` آلي. لا يعتبر timeout أو استجابة API ناقصة نجاحاً. **لا يتم إرسال تعليمات دفع إلى ERP من مرحلة MVP**.

## 9. الحوكمة والأمن والخصوصية

- عزل المؤسسات (tenant isolation)، أقل صلاحية، أدوار uploader/reviewer/approver/admin مع فصل المهام واعتماد ثنائي عندما تقتضيه سياسة الشركة.
- تشفير النقل والتخزين في الإنتاج، إدارة أسرار، سجلات أمنية غير قابلة للتعديل من مسار الواجهة العادي، حفظ مرجعية SHA-256 وسجل قرارات Append-only أو سجل محمي ومراقب.
- التحقق من النوع الحقيقي للملف وحدود الحجم والصفحات واستهلاك الذاكرة، ومعالجة الملفات ضمن sandbox، والحماية من zip bombs وPDF خبيث والمعادلات والروابط الخارجية.
- عدم تنفيذ تعليمات موجودة داخل المستند (prompt injection)؛ المستند مادة بيانات فقط؛ عدم إظهار الأسرار في logs أو artifacts.
- سياسة احتفاظ وحذف ونسخ احتياطي واسترجاع وفق عقد العميل، مع الحفاظ على متطلبات التدقيق وحدود الخصوصية.
- لا رفع فواتير حقيقية أو بيانات مرضى إلى CI أو منصات عامة؛ استخدم عينات اصطناعية أو بيانات منزوعة الهوية بموافقة صريحة.
- مصادقة API إلزامية قبل أي تعرض للشبكة، ولا نعتمد الإعداد المحلي الحالي كإعداد آمن لخدمة منشورة.

## 10. خطة العمل المرحلية

### المرحلة صفر — تدقيق حالة MDIA وتثبيت خط الأساس
**العمل:** قراءة `main` والوثائق الأربع، تحقق HEAD وPR #32 وCI وartifacts، جرد API وschema والاختبارات والأمان والتراخيص؛ إعادة إنتاج أرقام الاختبار وحساب denominator والـhash إن أمكن.  
**المخرج:** تقرير فني بالموجود/الناقص، قائمة أسباب الأخطاء مرتبة، وقائمة واجهات قابلة لإعادة الاستخدام.  
**بوابة الانتقال:** لا ادعاء «محرك جاهز» قبل وجود أدلة تشغيل على SHA محدد؛ لا دمج PR #32 تلقائياً.

### المرحلة الأولى — عقد البيانات وسلسلة الأدلة
**العمل:** مخططات PO/GRN/Invoice/Line/Evidence/Decision، واجهات adapters للـXML/Excel/PDF/OCR، حفظ مصدر القيمة، ضمان عدم تعديل الأصل، تحققات العملات والتواريخ والوحدات.  
**المخرج:** JSON schema، أمثلة متعددة اللغات، اختبار سلامة المصدر/الدليل، حالات رفض الاستدلال.
**بوابة الانتقال:** أي حقل مالي بلا مصدر واضح لا يُقبل كموثّق.

### المرحلة الثانية — محرك القواعد الحتمي
**العمل:** محرك Decimal، تحقق إجماليات، مطابقة المورد والمرجع والبند، partial GRN/invoice، duplicates/returns/credit notes، احتساب فروق الصفوف، isolation بالعملة.  
**المخرج:** تقارير الفروق مع القواعد والدليل، اختبارات وحدات وخواص وnegative cases.
**بوابة الانتقال:** لا أخطاء حسابية مرصودة في مجموعة تحقق شاملة للحالات المحددة، ولا تغيير للمستندات الأصلية.

### المرحلة الثالثة — تحسين الاستخراج العربي وتقييم النماذج
**العمل:** عزل أخطاء raw OCR عن أخطاء الجدول/ربط الصفوف عن أخطاء القواعد؛ اختبار PaddleOCR كخط أساس، ومقارنة DeepSeek-OCR وPaddleOCR-VL محلياً وفق جدوى العتاد والتراخيص؛ معالجة الصفوف العربية المقلوبة والمتداخلة دون إسقاط نتائج سابقة.  
**المخرج:** تقارير field-level وline-level وevidence-level لكل مخطط ومستند، ومقارنة السرعة/الموارد/نسبة المراجعة.
**بوابة الانتقال:** تحسن موثق على holdout مستقل دون إخفاء حالات فاشلة أو خفض معايير القبول.

### المرحلة الرابعة — واجهة التدقيق وسير المراجعة
**العمل:** شاشة عرض PO/GRN/Invoice جنباً إلى جنب، تمييز مصدر كل مبلغ، اختلافات مصنفة، تصحيح منفصل، توقيع/سبب قرار، تصدير تقرير تدقيق.  
**المخرج:** نسخة MVP محلية لشركة واحدة وملفات تجريبية.
**بوابة الانتقال:** يمكن للمراجع تعقب كل فرق إلى مصدره في وقت معقول؛ لا اعتماد آلي غير مقصود.

### المرحلة الخامسة — قبول ميداني محدود
**العمل:** تجريب مع شركات متطوعة وموافقة على المستندات، تقييم مستقل، قياس زمن الخدمة وتكلفة المراجعة ونتائج الأخطاء.  
**المخرج:** قرار Go/No-Go اقتصادي وتقني؛ لا إطلاق عام دون أمن وأذونات ونسخ احتياطي.
**بوابة الانتقال:** قبول مكتوب من صاحب العمل والتدقيق والأمن بعد الاطلاع على المخاطر المتبقية.

## 11. خطة الاختبار ومعايير القبول

### 11.1 مجموعات الاختبار
- **اختبار أولي:** 30 مجموعة (PO + GRN + Invoice = 90 مستنداً مبدئياً)، بمصادر عربية/إنجليزية وExcel/PDF نصي/PDF مصور وصور هاتف، مع بيانات صحيحة مرجعية يراجعها إنسان مستقل.
- **مجموعة موسعة:** 300+ مجموعة تغطي تنوع الموردين، المخططات، العملات والضرائب، تعدد الصفحات، الفواتير الجزئية، التحويلات والتكرار؛ عينات `train/dev/test/holdout` مفصولة، مع manifest وSHA لكل أصل.
- **اختبارات عدائية:** انقلاب OCR لرقم 1/7 أو 3/8؛ تبديل عمود السعر والكمية؛ نفس الرقم في سطر آخر؛ تلاعب evidence_id؛ صفحة أخرى؛ SKU متشابه؛ عربية مرئية ومعكوسة؛ قيمة «ريال» بلا نوع؛ دفعة متعددة العملات؛ تغيير المستند بعد الفحص؛ تكرار فاتورة؛ ملفات خبيثة وفشل محرك/timeout.
- **اختبارات تشغيل:** Windows / Docker / Linux، CPU فقط كخط أساس، اختبارات عدم الاتصال بعد تنزيل الأوزان، الأداء والذاكرة، rollback، الاستعادة، الأذونات، حفظ السجل.

### 11.2 مؤشرات القياس (كلها تُعرض بالأعداد والمقامات)
| المؤشر | التعريف | هدف قبول مرحلي |
|---|---|---|
| Exact critical fields | الحقول الحرجة المطابقة للمصدر من مجموعة مرجعية مستقلة | **100%** في مجموعة القبول المعلنة؛ لا تعميم |
| Silent financial false-match | إصدار `VERIFIED_MATCH` عند وجود خطأ معروف أو دليل ناقص | **0** في كل اختبارات القبول، خصوصاً العدائية |
| Known discrepancy recall | فروقات موثقة مكتشفة / كل الفروقات المعروفة | **100%** في مجموعة القبول؛ تتوسع باستمرار |
| Evidence chain integrity | كل قيمة مرتبطة بالمصدر الصحيح والصفحة/الخلية/السطر | **100%** للنتائج الآلية الموافق عليها |
| Spurious/missing line items | صفوف أضيفت أو سقطت دون وسم | **0** في مجموعة القبول |
| Calculations correctness | مقارنة Decimal والقواعد المرجعية واختبارات الخصائص | **100%** في مجموعات الاختبار المعتمدة |
| Review routing | كل نقص/غموض/تعارض معروف يصل `UNVERIFIABLE` | **100%** في مجموعة الحالات السلبية |
| Human-review share | الحالات التي تتطلب مراجعة / الإجمالي | **يُقاس، لا يُخفي ولا يُفرض له رقم مصطنع** |
| Processing time / cost | وقت الاستخراج + وقت مراجعة المستخدم والموارد | يُقارن يدوياً، وتُحدد حدود تجارية بعد التجربة |
| Reproducibility | نفس المصدر/الموديل/القواعد يعطي نتيجة قابلة لإعادة الإنتاج | نتائج موثقة مع versions/hashes |

**لا يُقبل إظهار دقة OCR مرتفعة مع ارتفاع «المطابقة المالية الخاطئة».** ليس المطلوب فقط 100% لحقول OCR؛ المطلوب أيضاً سياسة حظر تلقائي عند عدم اليقين. قد نحقق صفراً في أخطاء الاعتماد الآلي بالامتناع عن الاعتماد غير الموثق، لكن قد ترتفع مراجعات البشر؛ لذا نقيس **التغطية وجودة الخدمة معاً**. لا تتحول حالة `UNVERIFIABLE` إلى نجاح قرائي، ولا يمكن استبدال التقييم الحقيقي ببيانات مصطنعة.

### 11.3 شروط حظر الإصدار — P0
1. أي اعتماد مالي آلي مرتبط بقراءة OCR غير مؤكدة أو دليل غير صالح.
2. أي فرق مبلغ/عملة/سعر/كمية معلوم يمر مع قرار «مطابق» دون تفسير.
3. أي رقم مولّد بالتخمين ويقدم كقيمة من الفاتورة.
4. عدم القدرة على الرجوع للوثيقة الأصلية/نسختها والبصمة ومصدر كل قيمة حرجة.
5. إمكان تعديل النتائج الأصلية دون أثر تدقيقي أو جعل التصحيح البشري غير قابل للتتبع.
6. خلط بيانات مؤسستين أو تسريب مستندات/أسرار أو غياب آليات مصادقة مناسبة للنشر.
7. تجاوز اختبارات سلبية أو تغيير denominators أو استبعاد إخفاقات لإظهار `PASS`.
8. فشل الاختبارات الحرجة أو غياب إعادة إنتاج موثقة على commit SHA محدد.

### 11.4 أدلة التسليم المطلوبة لكل مرحلة
- SHA للفرع/commit، أسماء الملفات المعدلة، سبب التغيير، رابط CI ونتيجة الاختبارات.
- ملفات المرجع `manifest` مع SHA للعينات، مصدر ground truth وطريقة مراجعتها (من دون كشف بيانات حساسة).
- تقارير confusion/error: حقول صحيحة وخاطئة ومفقودة، صفوف زائدة، أخطاء الربط، false-match، نسب المراجعة حسب اللغة والتخطيط ونوع المصدر.
- أمثلة حالات فاشلة قابلة لإعادة الإنتاج، وقائمة المخاطر المفتوحة.
- تقرير فجوة ما بين نتيجة OCR وقرار التدقيق، مع الأدلة الأصلية.
- قرار قبول/رفض مكتوب، دون دمج أو إطلاق إذا ظلت شروط P0 مفتوحة.

## 12. نموذج تجربة المستخدم والنتائج

**ملف الحالة:** ثلاث بطاقات PO/GRN/Invoice → بيانات ووثائق أصلية → شريط حالة المصدر/التحقق → قائمة أصناف مرتبطة → اختلافات كمية/سعر/عملة → كل اختلاف يفتح النص الأصلي ومكانه → زر «اطلب مستنداً أوضح»، «اطلب تفسير المورد»، «أحِل للمراجع»، «اعتمد بقرار موثق» حسب الصلاحية.

**رسالة ناجحة نموذجية:** «مطابق ضمن قواعد PO/GRN والفاتورة وبحسب البيانات المتاحة، الإصدار X، مع أدلة لكل بند». **رسالة اختلاف:** «10 قطع مفوترة فوق المستلم؛ فرق 50 USD وفق الوثائق المرفقة». **رسالة امتناع:** «تعذر التحقق: سعر الوحدة غير مقروء على الفاتورة؛ لا قرار مالي».

**مخرجات:** JSON منظم، تقرير مراجعة PDF/Excel، ملخص مطابق/اختلاف/غير قابل للتحقق، حافظة أدلة، وتاريخ قرارات. لا إجراء دفع أو تعديل في ERP دون مرحلة دمج منفصلة وضوابط استحقاق/صلاحيات.

## 17. تعريف النجاح النهائي

**نجاحنا لا يعني أن OCR لا يخطئ.** يعني أن النظام لا يقدم قراءة غير مثبتة باعتبارها حقيقة مالية، ولا يصدر قراراً بالمطابقة دون أدلة وقواعد قابلة للفحص؛ يظهر عدم اليقين بوضوح، ويسجل التصحيحات والقرارات، ويثبت في الاختبارات أنه لا يُمرر أخطاء مالية صامتة معروفة. عندها يصبح المنتج **مدققاً مالياً مؤازَراً بالذكاء الاصطناعي** لا مجرد قارئ صور.

ومع ذلك، لا تعني أي نتيجة اختبار ضماناً قانونياً أو فنياً مطلقاً بأن الأخطاء مستحيلة؛ نطاق الضمان يجب أن يوصف بدقة، وتظل مراجعة الإنسان والضوابط التعاقدية جزءاً من نظام التحكم.
